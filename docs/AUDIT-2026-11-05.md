# Autumn Service Framework 代码审计（2026-11-05）

> 范围：`autumn-service-framework` 全仓（api / core / compiler / registry-extension / spring-boot / sample / spring-cloud-examples）
> 方式：逐文件静态审查 + 两处实机验证（可执行 jar 启动、端口占用启动）
> 基线：`mvn -o -B test` 全绿（core 8、compiler 1、registry 2、sample 12 其中 7 skipped）
> 说明：标「静态确认」的条目由代码路径直接推出；标「实测」的条目有运行日志；标「未验证」的条目没有跑通证据。

---

## 0. 结论速览

框架的主链路（Provider 启动、`@Export` 编译期装配、`@Reference` 运行时代理、三种注册中心、控制面）已经能跑通，但**连接池与控制面是当前最大的薄弱区**：连接池的借用超时单位写错、连接可能被静默丢弃或被重复入队、实例下线时会关闭正在使用的连接；服务端启动失败不会阻断注册，会把不存在的实例注册出去。这几条都不是"优化项"，而是会在并发或故障场景下直接产出错误结果的问题。

优先级建议：

| 级别 | 条目数 | 典型影响 |
| --- | --- | --- |
| P0 | 5 | 调用失败、连接泄漏/串用、实例不可用但注册仍在 |
| P1 | 18 | 配置不生效、资源不回收、无优雅停机、安全暴露 |
| P2 | 10 | 工程化、测试空白、死代码、文档偏差 |

## 1. P0：会导致调用错误或故障扩散

### P0-1 连接池借用超时的单位错误，「1s 超时」实际约 1 微秒

- 位置：`autumn-core/.../pool/impl/ConcurrentBag.java:71`、`autumn-core/.../pool/AutumnPool.java:67-71`
- 事实：`AutumnPool.borrow` 把毫秒值（默认 `1000`，Spring 注入 `10000`）传给 `ConcurrentBag.borrow(long timeout, TimeUnit.MILLISECONDS)`，但 `borrow` 内部直接 `handoffQueue.poll(timeout, NANOSECONDS)`，没有做单位换算。
- 影响：没有空闲连接时，等待窗口是 1~10 微秒，几乎立即返回 `null`，上层抛 `autumn reference no available instance`。文档 7 节承诺的"borrow 带超时（默认 1s）"不成立；并发一上来就会表现为随机失败。
- 附带问题：`ConcurrentBag.java:62-65` 的 `maxWaiters` 硬编码为 10，超过直接抛异常（不是排队），把并发压力转换成业务异常。
- 修法：统一用 `TimeUnit.MILLISECONDS` 换算成纳秒（或在 `AutumnPool` 直接传 `TimeUnit.NANOSECONDS` 对应的值），并让 `maxWaiters` 可配置、超限时排队而不是抛错。

### P0-2 连接可能被静默丢弃，或被重复入队后并发借出

三个独立写点共同破坏"一个连接同一时刻只属于一个借用者"的约束：

1. `ConcurrentBag.java:51-55`：`sharedList.poll()` 取出的 entry 若不是 `NOT_IN_USE` 状态，既不关闭也不放回，直接落到 `scale()`，**连接从所有队列消失**（socket 泄漏，`mapping` 里还留着一个永不归还的对象）。
2. `ConcurrentBag.java:177-194`：`add()` 在 `handoffQueue.offer` 成功后仍执行 `sharedList.add(entry)`。同一 entry 同时存在于两个队列；被 handoff 取走后，`sharedList` 里的副本再被 `poll` 出来时状态是 `IN_USE`，按第 1 条被丢弃；归还原连接后它又回到 `sharedList`，于是 `sharedList` 里可能出现同一对象的两个副本。
3. `ConcurrentBag.java:51-54`：`poll` 后不检查 `compareAndSet` 的返回值就 `return entry`。一旦出现第 2 条的重副本，两个线程可能都"成功"借到同一条 Thrift 连接。

- 影响：一条连接被两个线程同时写帧 → 协议错位、响应串包；或连接凭空消失 → 池容量持续下降，最终全部请求失败。
- 修法：`add` 成功后直接 `return`；`borrow` 改成循环 `poll`，非 `NOT_IN_USE` 或 CAS 失败就继续取（必要时重新放回）；丢弃路径必须 `close()`。

### P0-3 实例下线时会关闭正在使用中的连接

- 位置：`ConcurrentBag.java:230-253`（`remove(String ip)`）
- 事实：先 `v.setState(STATE_REMOVED)`（第 248 行），再判断 `if (v.getState() != STATE_IN_USE)`（第 249 行）。由于状态刚被改成 `REMOVED`，判断恒为真，**所有匹配实例的连接都会被 close，包括正在被 RPC 使用的连接**。
- 触发路径：`ExtensionDiscovery.refresh` 发现实例消失 → `AutumnPool.leave` → `bag.remove(ip)`；消费者每 5s 刷新一次，注册中心抖动或实例重启时必然触发。
- 影响：in-flight 调用报 transport 异常；借出方在 `finally` 里 `requite` 时状态已 `REMOVED`，再 close 一次；同一实例的其它健康连接也被一并关掉。
- 修法：先判断状态再置 `REMOVED`；`IN_USE` 的连接只标记、等 `requite` 时关闭；并且只在实例从快照中确实消失时才摘除。

### P0-4 `socketTimeout` / `connectionTimeout` 是死配置，下游挂死会拖死调用线程

- 位置：`ConcurrentBag.java:133-134`（`new TSocket(ip, port)` + `transport.open()`）、`AutumnBeanPostProcessor.java:245-246`（设置 10s 池超时、3s socket 超时）
- 事实：`ReferenceConfig.socketTimeout` / `connectionTimeout` 只被赋值，从未应用到 `TSocket`；池里所有连接都是无读超时、无建连超时的阻塞 socket。文档 5.2 把这两项列为可配置能力。
- 影响：Provider 进程卡住、网络半开、GC 停顿等情况下，消费者线程会无限期阻塞在 `read`，连接被长时间占住；池很快被占满，故障向上游扩散。
- 修法：`converter` 里显式 `tsocket.setConnectTimeout(...)`、`setTimeout(...)`；读超时抛出的异常必须**关闭连接而不是归还**。

### P0-5 服务端启动失败不阻断流程，仍会向注册中心注册（实测）

- 位置：`AutumnProvider.java:79-121`、`AutumnBootstrap.java:46-67`、`AutumnLifecycle.java:26-33`
- 实测：占住 30880 后启动可执行 jar，日志顺序为
  - `WARN autumn server start exception ... BindException: Address already in use`
  - `INFO multicast registered, instanceId:training-b:10.0.193.211:30880`
  - `INFO autumn framework started.`
  - 同时 stderr 打出 `Exception in thread "Thread-1" java.lang.RuntimeException`
- 事实：`start()` 只是起一个 daemon 线程，异常只在子线程里 `WARN` + `throw RuntimeException`；`serve()` 不等启动结果就注册；`AutumnLifecycle.start()` 无条件打印"started"。
- 影响：进程"启动成功"但实际没有服务端，注册中心里却多了一个不可用实例，流量持续打进来；容器编排的健康检查也看不出来。
- 修法：`start()` 做同步握手（`CountDownLatch` 等 bind 成功后再注册），失败向上抛并让 Spring 上下文启动失败；`/health` 与控制面返回真实监听状态。

## 2. P1：正确性、资源与运维缺口

### 2.1 连接池的容量与伸缩模型不成立

| 问题 | 位置 | 说明 |
| --- | --- | --- |
| 每次 `borrow` 未命中就为**所有实例**各新建一条连接 | `ConcurrentBag.java:86-123` | 没有目标连接数/最小空闲/最大总量，只有"每次 +1" |
| `active` 只增不减，到 500 后 `break` | `ConcurrentBag.java:106,112-114` | 500 是"扩容次数"而非"活跃连接数"；累计到 500 后不再扩容，池可能永久饥饿 |
| 建连在 `synchronized scale()` 内同步执行 | `ConcurrentBag.java:86,116` | 所有 `borrow` 争同一把锁，一个慢连接会阻塞整个服务的借用 |
| `ConsumerConfig.connections` 从未参与限流 | `ConcurrentBag.java:108-110` | 文档说默认 10，实际只是塞了个值 |
| 无空闲回收、无最小连接数、无泄漏检测、无健康检查 | `ConcurrentBag.java` 全文 | 没有 idle evict / maxLifetime / validation |
| `join()` 是死代码且除零 | `ConcurrentBag.java:255-276` | `config.getInstances().size()` 为 0 时 `ArithmeticException`；`avg>=1` 时循环第一轮就 `return`，只会建 1 条 |

### 2.2 并发与空指针

- `AutumnPool.referenceConfig` 的 `contains` + `put` 非原子（`AutumnPool.java:41-48`）：并发 `@Reference` 会建两个 bag，后 put 覆盖前者，前者的连接整体泄漏。应 `putIfAbsent` 或 `computeIfAbsent`。
- `AutumnPool.requite` 未判空 bag（`AutumnPool.java:82-83`）：bag 不在映射里时 NPE。
- `AutumnProvider.export` 用 `Map<Class, ServiceConfig>` 却 `containsKey(String)`（`AutumnProvider.java:57`）：重复导出检测恒为 false，而 `TMultiplexedProcessor.registerProcessor` 是普通 `HashMap.put`（libthrift 0.22 源码确认），重复导出会**静默覆盖**，且该 HashMap 在服务运行期被并发写时无任何保护。
- `ControlApiImpl.referenceConfig` 未判空（`ControlApiImpl.java:47-48`）：查询不存在的服务名直接 NPE，暴露给远程调用方。
- `ControlApiImpl.check`（`ControlApiImpl.java:54-76`）：新建裸 socket、无超时；`finally` 里 `transport.close()` / `tsocket.close()` 未判空，构造失败时再抛 NPE。

### 2.3 被声明但从未生效的配置与注解

| 声明 | 实际 | 位置 |
| --- | --- | --- |
| `@Export(name=...)` | 导出名始终是 `interfaceClass.getName()`，`name()` 无人读取 | `AutumnProvider.java:56-66` |
| `provider.timeout` | 只读入 `ProviderConfig.timeout`，从未使用（`tArgs.stopTimeoutVal(30)` 是停机超时，不是请求超时） | `ProviderConfig.java:92-98` |
| `socketTimeout` / `connectionTimeout` | 从未应用到 `TSocket`（见 P0-4） | `ReferenceConfig` |
| `ConsumerConfig.checkFail` | 定义后无任何消费方 | `ConsumerConfig` |
| `@Reference` 能标注 METHOD | 注入只遍历 `getDeclaredFields()`，方法注入未实现，父类字段也不处理 | `AutumnBeanPostProcessor.java:203` |
| `@Reference` 上的 `@Resource` 元注解 | `javax.annotation.Resource` 在 Spring 6/Boot 3 不再生效（Spring 用 `jakarta.annotation.Resource`），属于误导性残留 | `Reference.java:8,15` |
| `autumn.multicast.network-interface` | `ApplicationConfig` 有该项，`AutumnProperties` 没有对应字段，Spring Boot 下无法配置；文档 5.2 却列了出来 | `AutumnProperties.java`、`AutumnBeanPostProcessor.java:65-128` |

### 2.4 「零反射」承诺在消费侧不成立，生成代码未接入

- `AutumnBeanPostProcessor.createProxy`（`AutumnBeanPostProcessor.java:260-289`）每次调用都执行 `Class.forName(outer + "$Client")` + `getConstructor(...).newInstance(...)`，即**每次 RPC 一次反射建 client**。编译器生成的 `_XxxProxy`（`reference.ftl`）没有被 Spring 路径使用，只有示例/文档提到可以手工 `new`。
- `Object` 方法（`equals`/`hashCode`/`toString`）被代理到 handler 自身（`method.invoke(this, args)`），返回的不是 proxy 的语义。
- 建议：把 `_XxxProxy` 的构造改为可注入的工厂（`Class` → 代理实例，启动时解析一次），或在运行时缓存 `Constructor`；`Object` 方法直接本地实现。

### 2.5 没有优雅停机，`stop()` 只做了注销

- `AutumnLifecycle.stop()`（`AutumnLifecycle.java:36-46`）只调 `registry.shutdownHook()`；文档 4.3 声称"自动调用 `serve()` / `close()`"，但 `AutumnBootstrap` 根本没有 `close()`。
- 没有对 `TServer` 的引用，`TThreadedSelectorServer` 无法 `stop()`；线程池、发现线程、连接池、multicast 接收通道都靠 JVM 退出。
- `serve()` 不幂等且无启动状态：重复调用会重复 `start()`（第二次 bind 必然失败）、重复注册、重复挂 shutdown hook（`AutumnBootstrap.java:46-77`）。

### 2.6 控制面无认证，且输出敏感配置

- `ControlApi` 与业务服务共用 30880 端口，无任何认证/来源校验（`AutumnProvider.java:103-108`）。
- `applicationInfo()` 直接返回 `ApplicationConfig.toString()`，其中包含 `consulToken`、`nacosAccessToken`（`ControlApiImpl.java:34-37`）；`providerInfo()` 返回线程池与绑定 IP。
- 任何能连到该端口的人都能读到注册中心凭据、探测实例拓扑。
- 建议：默认只绑 `127.0.0.1` 或独立管理端口 + 白名单/token；`toString` 输出脱敏。

### 2.7 配置读取依赖 Spring Boot 的 nested 文件系统

- `CommonUtil.readClasspath`（`CommonUtil.java:116-153`）对 `url.toURI()` 的结果直接 `Path.of(uri)`，没有任何 `try/catch` 降级。
- 本次实测：Spring Boot 3.5 可执行 jar 启动正常（Boot 3.5 自带 `NestedFileSystemProvider`，能解析 `jar:nested:`）。
- 但用 jshell 验证了普通 jar URL：`Path.of(new URI("jar:file:/d:/tmp/app.jar!/application.properties"))` 抛 `FileSystemNotFoundException`。也就是说，非 Spring Boot 打包（普通 jar / WAR / 旧版 Boot）会在这里抛 `RuntimeException`；`url == null` 时回退的 `/opt/autumn/` 在 Windows 上会被解析成当前盘符根（如 `D:\opt\autumn`），与 Linux 语义不一致。
- 建议：改为 `url.openStream()` 读，找不到时返回 `null` 或明确抛业务异常；`/opt/autumn` 用可配置的 `autumn.config.dir` 替代。

### 2.8 注册发现的边界问题

- `MulticastBackend.register` 的 `published` 只允许发布一次（`MulticastBackend.java:75-78`），进程内二次注册（devtools 重启、多上下文）会被静默跳过；`deregister` 直接 `multicast.close()`（`MulticastBackend.java:85-88`），会同时关掉接收通道。
- `ExtensionDiscovery.refresh` 的 `setLabel(instance.getTraffic())` 每次覆盖（`ExtensionDiscovery.java:155`），泳道信息只能来自实例元数据，没有本地兜底。
- 网卡选择有两套逻辑：`CommonUtil.getNetIf`（按 Intel/Realtek 等名称匹配、过滤 `isVirtual`）与 `MulticastDiscovery.resolveNetworkInterface`（取第一个支持组播且有 IPv4 的网卡，不过滤 `isVirtual`）。多网卡机器上可能出现"注册 IP"与"组播出口"不是同一张网卡，跨机发现不通。
- `remove(String ip)` 的粒度是 IP，不是 `ip:port`（`ConcurrentBag.java:230`），同机多实例（不同端口）会互相误删。

### 2.9 编译器与生成的装配代码

- `ExportServiceProcessor` / `ReferenceServiceProcessor` 都用 `generated.compareAndSet(false, true)` 只生成一轮（`ExportServiceProcessor.java:69`、`ReferenceServiceProcessor.java:51`）。后续 round 才出现的 `@Export`/`@Reference` 类型不会被生成，静默回退到运行时反射（有日志 WARN，但不失败）。
- `MetaHolder` 是静态可变状态（`MetaHolder.java:17-19`），跨编译单元/同一 javac 进程复用时不隔离；`serverPort` 是死字段。
- 两个处理器都 `@SupportedSourceVersion(RELEASE_17)`，项目实际 source/target 21（日志会出现"less than -source 21"告警）。
- `autumn-compiler/pom.xml` 把 `spring-boot`、`logback-core/classic` 作为非 optional 依赖（`autumn-compiler/pom.xml:28-35,57-60`）：注解处理器会把这些带进使用方构建 classpath，且 `spring-boot` 在处理器中并无用途。
- CGLIB/AOP 代理的 bean 上 `@Export` 不生效（`export.ftl` 的 `supports` 用 `implClass == XxxImpl.class`，`AutumnBeanPostProcessor` 用 `bean.getClass()` 判注解），Spring 事务/切面场景会退回反射或用代理类导出失败。

### 2.10 示例与测试卫生

- `autumn-sample-boot-provider` 的 `SomeServiceImpl` 上有一个从不使用的 `@Reference(refer="consumer")`（`SomeServiceImpl.java:29-30`）：provider 启动时会 watch 一个永远不存在的服务，并为其建 bag。
- `MulticastDiscoveryTest` 是学习用代码（`System.in.read()` 死等、`System.out` 调试、`Send2/Rec2` 未使用字段），7 个 `@Disabled`。
- `AutumnPoolTest` 是空壳：只 `log.info` 打印路径和 JDK `ConcurrentLinkedQueue` 的 poll 行为（`AutumnPoolTest.java:12-32`），**没有任何连接池/并发/超时测试**。
- 无 `@SpringBootTest` 集成测试；`ThreadUtilTest` 单例耗时 17.7s（含 sleep）。

## 4. 功能缺失（Roadmap 对照 + 文档未列项）

### Roadmap 已列（`USER_GUIDE.md:610-617`）

| 项 | 代码现状 |
| --- | --- |
| `AutumnFilter` 过滤器链（鉴权、限流、链路透传） | 只有半成品 `AttachableProcessor` / `AttachableBinaryProtocol`：服务端 `protocolFactory` 仍是 `TBinaryProtocol.Factory()`（`AutumnProvider.java:96`），`in instanceof AttachableBinaryProtocol` 永远为假；客户端也没有写入 attachment。整套机制**未接线**，且依赖反射 `TFramedTransport.readBuffer_`，与 native 目标冲突 |
| 控制面治理工具（服务列表/上下线/路由） | 只有 5 个只读方法 |
| `checkFail` 熔断与降级 | 字段存在，无逻辑 |
| 直连/Consul 下 `@Reference` 配置增强 | `ipPort` 只支持 `ip:port` 两段，无超时/重试/权重 |
| GraalVM Native 示例与 CI | 无 native profile、无 IT，`AttachableBinaryProtocol` 反射会阻断 native |
| module-info / JPMS | 无 `module-info.java`，无 `provides` |

### 文档未列但明显缺失

- **负载均衡**：`sharedList` 是 FIFO，多个实例的可用性取决于 `requite` 顺序；没有轮询/最少连接/权重/泳道（`traffic` 只写入元数据，消费侧不筛）。
- **调用治理**：无重试、无超时治理、无熔断、无限流、无舱壁；示例自己写了 3 次重试（`SomeServiceConsumer.java:26-43`）。
- **可观测性**：无 metrics（Micrometer/Actuator）、无 tracing、无调用耗时统计；只有日志，且 `ConcurrentBag.java:68,79` 是 INFO 级热路径日志（高并发下日志风暴）。
- **健康检查**：`Discovery.checkHealth()` 空实现；控制面 `health()` 永远返回 `OK`，不反映监听/依赖状态。
- **安全**：无 TLS、无鉴权、控制面与业务同端口。
- **协议能力**：只支持 `TBinaryProtocol + TFramedTransport`，无 compact、无压缩、无异步客户端（生成代码里有 AsyncClient，但框架未暴露）。

## 6. 建议的修复顺序

**第一批（P0，1~2 天）**

1. `ConcurrentBag.borrow`：换算超时单位、循环取连接、丢弃前 `close()`、检查 CAS 结果。
2. `ConcurrentBag.add`：offer 成功后 `return`；`requite` 先置状态再 offer。
3. `ConcurrentBag.remove(ip)`：先判 `IN_USE` 再置 `REMOVED`；`IN_USE` 只标记不关闭。
4. `TSocket` 应用 `connectionTimeout`/`socketTimeout`；读超时异常时关闭连接而非归还。
5. Provider 启动改为"bind 成功才注册"，启动失败让 Spring 上下文失败。

**第二批（P1，3~5 天）**

6. 池模型：`maxPoolSize`/`minIdle`/`idleTimeout`/`maxLifetime`/健康校验；`scale` 移出锁；`active` 与连接数解耦；删掉或修好 `join`。
7. `referenceConfig` 改 `computeIfAbsent`；`requite`、`ControlApiImpl` 补判空；`export` 的 `containsKey` 改 `Class` 键。
8. 生命周期：`AutumnBootstrap` 增加 `close()`，持有 `TServer` 并 `stop()`，`serve()` 幂等；`stop()` 关发现/池/通道。
9. 控制面：独立端口或绑本机、加 token、`toString` 脱敏。
10. Spring 配置补齐 `autumn.multicast.network-interface`；`@Reference` 支持父类字段与方法注入（或收窄注解 `@Target`）；删除 `@Resource` 元注解。
11. `_XxxProxy` 接入 Spring（启动时生成一次工厂/缓存 Constructor），去掉 per-call `Class.forName`。
12. 编译器：按 round 累积生成、`RELEASE_21`、依赖改 `provided/optional`、`MetaHolder` 改为按 processingEnv 隔离。

**第三批（P2，按版本）**

13. 负载均衡（轮询/最少连接 + `traffic` 过滤）、重试、超时、熔断、限流。
14. Metrics/Tracing/Actuator 健康端点；把 `AttachableProcessor` 真正接到服务端协议工厂（或删除半成品）。
15. 依赖治理（`dependencyManagement`）、CI、LICENSE、示例去重。
16. 测试：连接池并发/超时/摘除、Provider 启动失败、Spring 上下文端到端、编译器多 round；删除交互式 demo 测试。
