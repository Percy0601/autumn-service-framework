## 0. 本次新发现（未被原 AUDIT 覆盖）

### [P0] 连接泄漏：`discard()` 不会关闭借出中的连接
- 路径：`AutumnPool.discard` → `ConcurrentBag.discard` → `ConcurrentBag.remove(entry)`
- 证据：`ConcurrentBag.java:340-365`，`remove(entry)` 当状态为 `IN_USE` 时仅 `compareAndSet(IN_USE→REMOVED)` 后 `return`，**不调用 `closeQuietly`**。
- 触发：调用失败路径（`reference.ftl:39` 与 `AutumnBeanPostProcessor.java:298`）在 `catch TException → discard` 之后**不再 requite**。于是该连接从 `mapping` 移除（`total` 递减），但底层 socket 永不关闭 → **永久连接泄漏**，池容量单调下降。
- 修法（最小改动）：让 `ConcurrentBag.discard(entry)` 在 `remove(entry)` 之后显式 `closeQuietly(entry)`（幂等；`REMOVED` 的持有者后续 `requite` 仍会再次安全 close，无副作用）。`evict`/`remove(ip)` 路径不经过 `discard`，保留"IN_USE 推迟关闭"语义。

## 4. 安全 / 运维缺口（原 AUDIT 未修复项，仍成立）

- **控制面无访问控制**：`ControlApi` 与业务共用 30880，`ControlApiImpl` 无任何认证/来源校验（脱敏已做，但无访问控制）；`health()` 永远返回 `OK`，不反映真实监听/依赖状态。
- **无独立管理端口、无 TLS、无 token**。
- **无负载均衡**：`sharedList` 是 FIFO，无轮询/最少连接/权重/`traffic` 泳道筛选（元数据写入但消费侧不筛）。
- **无调用治理**：无重试/熔断/限流/舱壁（示例自行写了 3 次重试）。
- **无可观测性**：无 Micrometer/Actuator/tracing；`ConcurrentBag` 部分热路径日志为 INFO 级，高并发下日志风暴。
- **GraalVM Native**：无 native profile/CI；`AttachableProcessor` 反射会阻断 native-image。

## 5. 默认值与配置陷阱

- **Provider worker 线程池默认 `corePoolSize=0 / maxThreads=1`**（`AutumnProperties`/`ProviderConfig` 默认 `max-threads=1`）。`ThreadPoolExecutor(0,1,...)` 在 core=0 时新任务先入队，实际**服务端串行处理**请求，不适合任何生产负载（README 已注明但未强调风险）。建议默认至少 8~几十。
- `@Reference` 直连 `ipPort` 仅支持 `ip:port` 两段，无超时/重试/权重。

## 7. 部署验证（2026-11-05，虚拟机 percy@192.168.0.102）

> 目标：验证"修复后"的框架在真实 consul 注册中心下，两个 provider 实例能被消费端负载均衡。

### 环境
- 虚拟机：`percy@192.168.0.102`（Ubuntu，password `1`，已配 SSH 公钥免密）。
- Consul：`1.20.1`（`~/tools/bin/consul agent -dev`）。
- JDK：`openjdk 21.0.12.1`（apt `openjdk-21-jdk-headless`）。
- 部署物：`autumn-sample-boot-provider` × 2（thrift 端口 30880 / 30881，HTTP 8080 / 8082）+ `autumn-sample-boot-consumer`（HTTP 8081），均通过命令行参数覆盖 `autumn.registry-type=consul`、`autumn.consul.host/port`、`autumn.provider.port`、`autumn.provider.ip=127.0.0.1`。

### 结果
- 两个 provider 均成功在 consul 注册：`training-b` 出现 `127.0.0.1:30880` 与 `127.0.0.1:30881` 两个健康实例。
- 消费端 `GET /boot-sample-consumer/hello` 连续 12 次请求，响应中的 `[node:PORT]` **交替命中 30880 与 30881**（严格轮询），证明：
  - consul 注册 / 发现链路打通；
  - 编译期生成的 `_SomeServiceProxy`（零反射消费侧）生效；
  - 编译期生成的 `_SomeServiceImpl*ServiceRegister`（assembler，零反射导出侧）生效；
  - `@Reference` 注入、`SomeServiceImpl.echo` 链路正常。
- 结论：**修复项在真实 consul 多实例场景下验证通过，负载均衡正常。**

### 验证中新发现的 Bug（已修复）
**[P0] `ExportServiceProcessor` 生成的 `META-INF/services/...AutumnServiceAssembler` SPI 文件写错了类名。**
- 现象：provider 启动即抛 `java.util.ServiceConfigurationError: ...AutumnServiceAssembler: xyz.wewin.autumn.sample.boot.provider.service.SomeServiceImpl not a subtype`，Spring 容器初始化失败，provider 无法启动。
- 根因：`writePending()` 把 `written`（实现类 FQN，如 `SomeServiceImpl`）写进了 SPI 文件，而不是生成的 assembler 类（`_SomeServiceImplServiceRegister`，才真正实现 `AutumnServiceAssembler`）。实现类不实现该接口 → `ServiceLoader` 校验失败。
- 修法：`writePending()` 改为收集生成类的 FQN（`generatedAssemblers` 累积集合，跨多 round 安全），只把生成的 `*ServiceRegister` 写进 SPI 文件；并补 `LinkedHashSet` import、删除废弃的 `AtomicBoolean` import。
- 影响：所有带 `@Export` 的模块此前在 consul/multicast 真实启动下都会因此崩溃（之前未端到端跑通过）。consumer 侧 `_SomeServiceProxy` 由 `Class.forName` 加载，不走该 SPI，故未受影响。

### 8.6 Native 端到端验证中发现并修复的问题

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| 三个 native 进程启动即退出：`MissingReflectionRegistrationError: Cannot reflectively invoke method 'org.apache.coyote.AbstractProtocol.getProperty(String)'` | Boot 的 `TomcatWebServer#disableBindOnInit` 经 `Connector#getProperty("bindOnInit")` → `IntrospectionUtils` 反射调用 `AbstractProtocol#getProperty` / `setProperty`；Spring Boot 内置 AOT hints 未覆盖这些方法，GraalVM 25 严格反射检查直接抛错 | `ProviderNativeHints` / `ConsumerNativeHints` 显式注册 `org.apache.coyote.AbstractProtocol`、`Http11NioProtocol`、`org.apache.catalina.connector.Connector` 的 public/declared 方法；本地 `mvn -Pnative package` 确认生成的 `reflect-config.json` 含 `allPublicMethods`/`allDeclaredMethods` 后重建镜像 |
| consumer 首次调用全部 500：`IllegalArgumentException: Object of class [GenericApplicationContext] must be an instance of AnnotationConfigRegistry` | Spring Cloud Commons 4.3.3 的 `LoadBalancerClientFactory`（`NamedContextFactory` 子类）运行时创建子应用上下文；Boot AOT 下该上下文为 `GenericApplicationContext`，而 `NamedContextFactory#registerBeans` 断言其必须实现 `AnnotationConfigRegistry`，Native 下首次 `choose()` 必崩 | `HttpExchangeConfig` 的 `lb://` 过滤器改用 `DiscoveryClient`（Consul 真实服务发现）+ `AtomicInteger` 原子轮询重建 URI，绕开动态子上下文；与该文件中原有"手工装配规避 Spring Cloud Commons `lb://` scheme 缺陷"的思路一致。`BasicController` 的 `block` 超时由 1s 提升到 5s，避免首次 Consul 查询超时 |

**遗留**：TLS、熔断/限流/重试/舱壁、Micrometer/Actuator/tracing、逐调用 control token 校验仍按第 6 节第 7 条做版本规划，未在本轮塞入半成品。
